# Issue 337 — Contacts with optional email and Telegram (Implementation Plan)

## 1. Scope (what to implement)

Make local contacts independent of email. A user can create a named participant with optional email and Telegram, reuse the person in other meetings, and manually link a transcript speaker to that participant. Extend the existing contact card to edit details and open a unique Telegram username through `t.me`.

**Blast radius:** local contacts, `notes.participants` JSON and its first-processing freeze state, run speaker corrections, voice-profile contact associations, shared person profiles, calendar-to-note materialization, manual speaker assignment, Home participant displays, AI participant material, editor mentions and action-item owner tags, transcript export, and Notes CLI reads. Calendar-provider attendee payloads and Google People ingestion still use external email attributes. No Telegram API, authentication, or messages are involved.

**Criticality:** a broken migration can make contacts or speaker associations unavailable or associate the wrong person. Invalid participant handling can omit people from prompts or speaker-count hints. A failed edit must not partially change saved contact data. Audio, raw provider output, historical summaries, correction provenance/revisions, and voice embeddings must not change during identity migration.

**Rollback:** this is a one-way schema and reference migration; reverting code alone is insufficient after the migrated profile is opened. Before a real-profile upgrade, quit Gristmill and make a consistent copy of the entire profile, including SQLite state and managed files. No automatic backup is assumed or added. Recovery requires quitting the app, restoring that pre-upgrade profile and using its matching app version. This discards later edits/recordings unless those are separately preserved; an automatic reverse conversion cannot represent name-only contacts. Implementation and smoke checks use only disposable synthetic profiles, never the user's profile.

**Irreversible effects:** after the first successful migration commit, the profile no longer has the old email-keyed identity representation. Subsequent creation of contacts without email cannot be represented by the previous version. No external writes or deletion of audio/content are planned. Restoring a pre-upgrade copy cannot retain subsequent changes by itself.

Out of scope: separate address book, Telegram numeric IDs/account verification/chat import, automatic contact merging, new automatic attribution rules, capture/provider changes, new infrastructure/dependencies, and dual contact identity paths. The only approved compatibility exception is reading existing persisted mention links; it does not retain old contact mutation APIs or rewrite stored note/Summary text.

## 2. Fixed decisions (must follow)

1. Follow `AGENTS.md`, `.memory-bank/steerings/quality.md`, `type-safety.md`, `documentation.md`, and `project-commands.md`. Use the canonical runner. All tests, examples, screenshots and metadata are fully synthetic.
2. Use an integer SQLite contact ID as the stable local identity. Preserve the existing name sources (`learned_name`, `people_name`, `display_name`) and photo, with the current name priority. New manual creation requires a non-blank name. Existing imported unnamed contacts remain usable; do not invent names for them.
3. Email is nullable and unique when present, with the existing trim/lowercase semantics. Convert missing, null, empty and whitespace-only email to SQL/DTO `NULL`, including legacy participants with `email: ""`; never create an empty email identity. Names are not unique. Email edits or removal do not change contact ID or existing participant/speaker links.
4. Store nullable `telegram_username`, without `@`, a URL prefix or outer whitespace. Accept `username`, `@username`, `t.me/username`, and `https://t.me/username` (one optional trailing slash on a link). Extract and validate the username against `^[A-Za-z0-9_]{5,32}$`. A link must have exactly host `t.me` and one username path segment, without credentials, port, query or fragment. Reject host-only URLs, invite/phone links, post links, other hosts/schemes, internal whitespace, repeated `@` and other characters. Do not perform network resolution. Preserve entered letter case for display, compare without regard to ASCII case and enforce a unique database index with `COLLATE NOCASE`. An empty field becomes `NULL`; permit multiple nulls. This task supports the agreed 5–32 character basic-username format, not shorter collectible aliases or numeric Telegram IDs. Format reference: [Telegram account.checkUsername](https://core.telegram.org/method/account.checkUsername); usernames/links reference: [Telegram FAQ](https://telegram.org/faq#usernames-and-t-me).
5. A collision rejects the whole contact mutation, returns a typed conflict result, and keeps saved data unchanged. A same-contact save/case edit is allowed; clearing a username releases it. For a create-time email conflict, return the existing contact ID and offer an explicit action to select that contact instead; selection must not overwrite it with the proposed name or Telegram. For an edit-time email conflict, keep the original contact, all fields, and all participant/speaker links unchanged and show a clear message identifying the existing contact. Manual merging and reassignment of existing links are outside this task. In particular, a name-only contact cannot absorb a People contact's occupied email in this version; selecting that other contact elsewhere does not transfer existing speaker links. Do not merge contacts, transfer a username, or add remote availability checks.
6. Build `https://t.me/<username>` from the saved username as one escaped URL segment and use `src/utils/externalLinks.ts`. Display `@username`; show no open action when absent. There is no direct `tg:` route.
7. Local participant selection, cache keys, contact mutations, run corrections and voice-profile contact associations use contact IDs. Distinguish a contact ID from the existing voice-profile ID and speaker ID. Email may remain in display/export/provider projections as an attribute, never as a second local link identity.
8. Keep calendar transport `CalendarAttendee` separate from the local note-participant schema. Local note participants carry `contactId` plus `displayName`, nullable `email`, RSVP and self fields. Name/email fields are provisional on addition/materialization: immediately before the note's first AI naming/Summary processing snapshot, refresh them once from current contacts by ID, using `learned_name`, then `people_name`, then `display_name`, with the provisional meeting name as the last fallback. Freeze that participant context durably at this point, not when the calendar note is created. It is then authoritative for AI input, CLI participant name/email, transcript export and Summary freshness. Contact cards, profile avatars, contact search and new participant selection continue to use current contacts. Ordinary contact edits/People refresh after the freeze do not rewrite existing meeting snapshots, generated text or Summary status. Retries and later processing runs do not re-enrich a frozen context. Adding/removing participants and explicit speaker corrections retain their existing freshness effects; a participant added after the note is frozen gets a snapshot at that explicit addition. Resolve incoming calendar attendees by normalized email and preserve provider RSVP/self metadata and event association behavior.
9. Remove old contact request aliases, general email-keyed profile caches and email-based local speaker links. External calendar ingestion still resolves email attributes to contact IDs. **User-approved persisted-mention exception:** new contact-bound mentions use `mention:contact:<positive-contact-id>`. Existing `mention:<encoded-email>` links remain readable through a scoped read-only resolver; existing label-only links remain readable without a guessed contact association. Keep their saved label and href unchanged when parsed, rendered or round-tripped. Do not migrate text, rehash content, or restore email-based contact writes for this reader.
10. Manual correction accepts an optional participant contact ID and verifies membership in that run's owning note before any correction/name write. A missing, invalid or other-note contact ID is rejected without side effects. Keep Only this meeting as the default when the dialog opens. Do not change automatic naming priority, selected-transcript projection guards, raw artifacts, Summary text, or voice-profile training policy.
11. Freeze `draft.md`. Record later planning decisions here. Update permanent docs by feature; do not link them to `.tasks/`, edit past task folders, or rewrite accepted ADRs. This contact-schema change does not itself revise a recorded ADR.
