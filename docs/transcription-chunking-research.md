## Текущее решение — только запись во время встречи

Тимур отказался и от черновика: во время встречи только сохраняем mic/system. После Stop финализируем запись, выполняем обычный file ASR с диаризацией и строим заметки. Актуальная схема и проверки: [record-then-process.md](record-then-process.md).

**Остальная часть этого документа — историческое исследование отвергнутого варианта обработки во время встречи.** Описанные ниже минутные окна, overlap, live-очередь, локальный черновик и согласование спикеров между фрагментами не являются задачами первой версии. Ссылки на код сохранены как источники; прежние рекомендации не переопределяют текущее решение.

Исходный список проектов взят из [обсуждения](https://chatgpt.com/share/6ab3de0a-0588-83eb-a555-d523389afdbe). Проверены текущие снимки 15 репозиториев: README, дерево и выбранные файлы захвата, сегментации, транскрипции, диаризации и восстановления. Это чтение кода, не испытание приложений и не сравнительный тест качества моделей. Ссылки на код закреплены на конкретных коммитах. ## Исторический вывод для фрагментной обработки

Сценарий осуществим: независимо сохранять исходные mic/system, закрывать небольшие аудиофрагменты и отправлять их обычными HTTP-запросами, пока запись продолжается. Готовый текст добавляется постепенно. После Stop сохраняется хвост и обрабатывается остаток очереди.

Лучшие ориентиры по отдельным частям: **Ledgeur — простой алгоритм границ; Anarlog — VAD и точные позиции в аудио; Screenpipe — восстановление обработки; Homan — разделение исходной записи и временных фрагментов; Heed — общая работа с голосами двух дорожек.** Готового проверенного образца всего нашего сценария с ElevenLabs, Deepgram и Gemini среди прочитанных путей нет.

## Четыре разных размера

Не стоит называть одним словом «чанк» четыре разных объекта:

1. **Буфер захвата** — небольшой блок PCM из CoreAudio/AudioWorklet. Его размер определяется захватом.
2. **Файл исходной записи** — ограниченный по размеру, восстанавливаемый после аварии кусок дорожки.
3. **Фрагмент ASR** — временной диапазон дорожки, упакованный в самостоятельный файл для одного запроса. Может пересекать границы файлов записи.
4. **Сегмент ответа** — слово/реплика с метками времени от провайдера.

Делать четыре фреймворка не требуется. Достаточно записи файлов, метаданных диапазонов и одного runner. Но привязка каждого ASR-запроса к каждому callback захвата создаст слишком много запросов и плохие границы речи.

## Прежнее предложение прототипа — не реализовывать в текущей схеме

Следующие числа — **стартовая гипотеза**, не результат измерений качества ElevenLabs/Deepgram/Gemini.

| Настройка | Начальное значение / правило |
| --- | --- |
| ASR target | 60 секунд аудио на дорожку |
| Поиск границы | После target ждать паузу примерно 0,8 секунды на этой дорожке |
| Hard maximum | 90 секунд; монолог не должен держать результат бесконечно |
| Принудительный разрез | Искать тихую точку в последних 1–2 секундах; если её нет, резать по лимиту |
| Padding речи | Если обрезаем внешнюю тишину, оставлять около 0,3 с до речи и после неё |
| Параллелизм | Начать с двух запросов всего; по одному на дорожку. Учитывать лимиты конкретного аккаунта |
| Stop | Закрыть и поставить в очередь весь оставшийся речевой хвост, независимо от target |
| Тишина | Исходник хранится целиком. Достоверно пустой ASR-интервал можно отметить обработанным без запроса; сомнительное тихое аудио отправлять |

Пауза определяется отдельно для mic и system: одновременная тишина обоих источников не обязательна. Короткое «да» сохраняется внутри большого фрагмента; отсутствие новых слов не повод удалять исходное аудио. Внутренние паузы не вырезаем и разрозненные реплики в «речевой коллаж» не склеиваем: иначе понадобится отдельная обратная карта времени.

На первом сравнении проверить **30, 60 и 120 секунд** на одинаковых записях. 60 с — разумная точка начала при согласованном допуске на задержку. Реальная задержка включает накопление, ожидание паузы, очередь, загрузку и ASR. «Чанк 60 с» не означает «текст появится ровно через 60 с».

### Нужно ли перекрытие

На хорошей паузе начать с соседних диапазонов без повторной отправки аудио. Сохранённые тишина и небольшой padding защищают края от слишком агрессивного VAD.

Для принудительных разрезов сравнить два варианта: без overlap и с небольшим контекстом порядка 1 с вокруг границы. Добавлять overlap в основной путь стоит при подтверждённых потерях слов на стыках. Он требует устранения дубликатов и увеличивает оплачиваемую длительность. Не нужно каждый раз отправлять весь накопленный разговор.

Если overlap понадобится:

- Хранить отдельно диапазон входного аудио и диапазон, за который отвечает фрагмент.
- Переводить слова в общую шкалу времени; сопоставлять только результаты соседних фрагментов в области перекрытия.
- Учитывать время и текст вместе; не удалять совпадающие фразы по всему транскрипту.
- При несовпадении границ слов использовать детерминированное правило владения стыком и сохранять исходные ответы. Метки времени ASR приблизительны: один лишь фильтр по середине слова не гарантирует отсутствие потерь.
- При необходимости задерживать публикацию небольшой спорной области до соседнего результата. Основной готовый текст не должен постоянно переписываться.

Показательный нюанс: в [Screenpipe `flush_audio`][screenpipe-flush] хвост, названный overlap, отделяется **до** отправки. Для обычного большого буфера это перенос хвоста в следующий запрос, а не повторение хвоста в двух запросах. Нельзя заимствовать алгоритм только по имени переменной.

### Как отправлять

Один закрытый фрагмент — один обычный запрос. Для первого прохода подходит самостоятельный WAV с корректным заголовком; FLAC можно выбрать при измеримой выгоде для загрузки. Не передавать произвольные куски контейнера как независимые аудиофайлы. Исходные дорожки сохранять без потерь; ресемплинг и AEC делать на производной копии, в соответствии с требованиями выбранной модели. Универсальное требование «всегда 16 кГц» для исходника не нужно.

Из двух дорожек сначала делать независимые запросы. `system` может содержать несколько людей, `mic` — эхо и людей в комнате; канал не равен человеку. Результаты объединять по времени, сохраняя возможную одновременную речь. Эхо обрабатывать отдельно от overlap между соседними фрагментами: это разные причины повторов.

Если API поддерживает словарь/контекст, передавать проверенные термины поддерживаемым параметром. Не подмешивать предыдущий текст в аудио и не обещать универсальную передачу контекста между этими тремя API.

## Время, очередь и восстановление

Для каждого диапазона достаточно знать: recording ID, source/epoch, начало и конец в сэмплах, формат/частоту, выбранную конфигурацию ASR, статус, попытки и сохранённый результат. Точные поля схемы здесь не утверждаются.

Абсолютное время слова вычисляется из начала отправленного диапазона и относительной метки провайдера. При обрезке начальной тишины сдвиг меняется. При перезапуске устройства появляется новый epoch с привязкой к общей монотонной шкале. Время завершения HTTP-запроса для этого непригодно. Пропуск захвата остаётся отмеченным пропуском; его нельзя скрывать сжатием времени.

Минимальный порядок:

1. Сохранить аудио и закрыть диапазон. Зафиксировать метаданные до начала ASR.
2. Восстанавливаемая запись задания в существующем SQLite; один runner в main/background процессе.
3. Выполнить запрос; сохранить ответ и публикацию результата с идентификатором задания. UI читает сохранённое состояние.
4. На повторе не добавлять те же сегменты второй раз. После перезапуска вернуть незавершённые задания в обработку, учитывая уже сохранённые ответы.
5. Сеть/429/временные 5xx — отложенный повтор с ограничением частоты и учётом Retry-After. Ошибка ключа/формата требует исправления; не запускать бесконечный быстрый цикл.
6. Если ASR отстаёт, растёт очередь на диске. Запись не ждёт HTTP; старые фрагменты не выбрасываются. При заполнении диска явно сообщить о проблеме записи.
7. Stop завершает захват, но не отменяет очередь. Summary запускается после обработки всех обязательных интервалов; при ошибке результат обозначается неполным.

Сбой между получением ответа провайдера и его локальным сохранением оставляет неопределённость. Без поддерживаемой серверной идемпотентности/получения результата нельзя обещать exactly-once или отсутствие повторной оплаты. Локальные дубликаты устраняются независимо от этой проблемы.

Начать можно с одной таблицы заданий и одного runner. Отдельный брокер, distributed leases, plugin framework и несколько вложенных очередей для этого не требуются. Восстанавливаемые файлы и состояние нужны непосредственно для уже заявленной работы без сети и после перезапуска.

## Диаризация между фрагментами

Номер `speaker_0` относится к конкретному ответу. Внутренний ключ должен включать запрос/фрагмент; совпадение номеров не доказывает совпадение людей. Прочитанные API не дают общей гарантии идентичности неизвестных людей между независимыми загрузками.

Во время встречи показывать готовый текст **без предварительных имён/номеров спикеров**, как предложил Тимур. Само ожидание Stop не исправляет идентичность: перед показом нужна выполненная процедура согласования.

| Способ | Что упрощает | Цена / ограничение |
| --- | --- | --- |
| Один общий provider-проход после Stop | Провайдер видит всю запись в одном контексте и сам строит набор спикеров. | Повторная обработка/оплата, возможное изменение текста, лимиты длительности. Для Gemini с diarization 30 мин — не универсальный вариант для длинных встреч. |
| Локальная диаризация всей дорожки после Stop | Можно сохранить уже полученный текст и наложить общие speaker turns по word times. | Локальная модель, время обработки, качество выравнивания. Heed показывает похожую общую обработку, но сам ещё и повторяет ASR; его pipeline нельзя считать доказательством варианта без повторного ASR. |
| Сопоставление голосовых embeddings сегментов разных запросов | Можно использовать диаризацию провайдера внутри фрагмента и не повторять ASR. | Это отдельный алгоритм: чистые голосовые отрывки, короткие реплики, смешанные голоса, confidence и глобальная кластеризация. Нельзя свести к сравнению номеров. |
| Зарегистрированные голоса провайдера | Например, ElevenLabs speaker library может узнавать известных людей. | Требует зарегистрированных голосов и зависит от провайдера; не решает автоматически всех новых участников. |

**Не делать собственное сопоставление спикеров обязательным первым шагом.** Сначала проверить уже имеющиеся локальные speaker-инструменты на общей записи и сравнить с одним provider-проходом на доступной длительности. Если качество общей диаризации приемлемо, она решает согласование без повторного распознавания каждого фрагмента. Если нет — выбрать явно более дорогой provider-проход или отдельную задачу на сопоставление. Выбор должен быть сделан до обещания пользователю корректных общих спикеров.

## Применение к OpenHercules

Текущий код проверен отдельно от upstream. Это перечень точек изменения, не выполненная миграция:

- `src/stores/meetingRecordingStore.ts` и `src/helpers/meetingCoordinatorIpcHandlers.ts`: отделить владение записью от подключения realtime ASR. Сохранение обоих оригинальных источников должно начаться независимо от облака. Сейчас временный mic-путь и system-путь предназначены для существующей диаризации, а не для гарантированной независимой записи всей встречи.
- `src/helpers/meetingAudioTimeline.ts`: переиспользовать идеи sample count и учёта пропусков; проверить, что шкала сохраняется на диске и переживает смену устройств.
- `src/stores/batchQueueStore.ts`: текущая UI-очередь не заменяет сохраняемую очередь обработки встречи.
- `src/services/fileTranscription.ts` и provider helpers: переиспользовать поддерживаемые file API, но сохранить word times и локальные speaker IDs. Deepgram сейчас помечен streaming-only в `src/config/transcriptionCapabilities.ts`; ElevenLabs нужно добавить; Gemini нужен контракт с метаданными транскрипции.
- `src/helpers/speakerEmbeddings.ts`: уже есть извлечение и сравнение embeddings. Это полезная заготовка, не готовое согласование всех фрагментов. Метод чтения WAV загружает файл целиком; не вызывать его заново для каждого короткого отрывка многочасовой записи.
- UI: отдельно показывать состояние записи и обработки; добавлять готовый текст; не объявлять встречу полностью обработанной при пропуске/ошибке задания; имена показывать после согласования.

## Что измерить перед выбором окончательных параметров

Взять несколько одних и тех же русских записей: разговор 1:1, 3+ человека, длинный монолог, числа/имена, короткие ответы, шум, одновременная речь и эхо без наушников. Сравнить 30/60/120 с, паузы и принудительные разрезы, затем только при необходимости overlap.

Фиксировать: пропуски/повторы в нескольких секундах от стыка; общую точность на размеченных отрывках; ошибки чисел/имён; задержку до готового текста; рост очереди; оплачиваемую длительность с повторами; стабильность спикеров. Отдельно проверить выключение сети, перезапуск во время upload/после ответа и Stop посреди речи. Облако в рамках этого исследования не вызывалось, качество и стоимость не измерены.
